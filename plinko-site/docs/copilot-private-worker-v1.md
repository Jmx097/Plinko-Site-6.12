# Plinko Pocket Copilot private worker

Version: 1.0 (`copilot-private-worker-v1`)
Status: reviewed implementation specification; infrastructure provisioning and runtime activation remain separately human-approved.
Owner: Plinko Pocket / CRM governance

## Decision

The Copilot runtime is one dedicated, tenant-isolated worker service. It is not the shared Hermes host, the `default` Hermes profile, public chat, a general agent runtime, or a browser-accessible service. Pocket is the only entry point. The worker executes only the reviewed `copilot-foundation-v1` R0/R1 catalog and cannot acquire new tools, browser/shell/filesystem access, CRM credentials, or external network authority.

This boundary favors predictable scope, privacy, and rollback over a lower-cost shared-agent implementation. It intentionally adds an internal Pocket-to-worker hop and durable queue, so a request may return `queued` rather than stream an unbounded live agent session.

## Deployment and network boundary

- Run the worker in a dedicated private compute project/host, distinct from the shared Hermes host and its persistent memory, profiles, chat gateway, tools, browser, filesystem mounts, and credentials.
- Bind the worker application and its health/metrics endpoints to private networking only. There is no public DNS record, public load balancer, browser route, webhook ingress, SSH tunnel for application traffic, or user-visible chat endpoint.
- Permit inbound traffic only from the Pocket server identity over the private network. Enforce both network allowlisting/mTLS and the signed application contract below; either missing check denies the request.
- Permit outbound traffic only to the fixed internal CRM broker, the approved model-provider endpoint, and required private persistence/telemetry endpoints. Egress is deny-by-default; DNS, HTTP proxy, arbitrary HTTP tools, package installation, shell, browser, filesystem, and metadata-service access are unavailable to the runtime.
- Keep the worker stateless except for ephemeral execution memory. Durable runs, attempts, artifacts, reservations, and audit events reside in the tenant-scoped Copilot persistence service. No customer context or CRM data is written to Hermes memory, host disk, or generic log streams.
- A deployment identity may read only its worker-specific secrets and cannot read Pocket/Clerk, CRM broker, database admin, shared Hermes, or other tenant secrets.

## Signed Pocket-to-worker contract

Pocket verifies Clerk identity, organization membership, `sales` + `crm.workspace` + `copilot.workspace`, signed selected-organization handles, request bounds, and the fixed tool catalog before enqueueing. The browser supplies only bounded reviewed-tool input and an advisory idempotency key; it never calls the worker.

Pocket sends one canonical JSON request body and an Ed25519 detached signature over the UTF-8 body. The dedicated worker stores only the active Pocket verification public key(s); the corresponding private key stays in Pocket's server-only secret store. Requests use private mTLS and these required headers:

| Header | Contract |
| --- | --- |
| `X-Copilot-Contract-Version` | Exact `copilot-worker-contract-v1` |
| `X-Copilot-Key-Id` | Active Pocket signing-key identifier, selected from a worker allowlist |
| `X-Copilot-Signature` | Base64url Ed25519 detached signature of the exact raw body |
| `X-Copilot-Request-Id` | UUID correlation identifier generated by Pocket |
| `X-Copilot-Sent-At` | UTC RFC 3339 timestamp; accepted skew is at most 60 seconds |

The canonical body has no raw CRM/Core IDs, credentials, direct contact methods, browser session material, free-form model prompt, endpoint, provider, model, or actor header. It contains only:

```text
{
  contractVersion, requestId, issuedAt, expiresAt,
  policyVersion, runId, idempotencyKey,
  tenant: { organizationId, membershipId, actorSubject },
  tool: { name, normalizedInput, opaqueRecordHandle? },
  limits: { inputTokenCap, outputTokenCap, artifactByteCap, costReservationUsd },
  trace: { pocketRequestId, correlationId }
}
```

The worker must reject before queueing if mTLS identity, contract version, key ID, signature, exact request/header ID match, timestamp/expiry, UUID shape, policy version, tenant scope, reviewed tool name/input bounds, opaque-handle shape, or limits are invalid. It records a redacted rejection audit event when audit persistence is available; otherwise it fails closed. `requestId`/`runId` and the signed body digest are unique within their organization. A replay, a signature valid for a different body, or an idempotency-key reuse with a different signed normalized request is rejected.

The worker returns a minimal internal response: `accepted | queued | in_progress | completed | cancelled | denied | unavailable`, the correlation/run identifiers, and no model output or CRM DTO beyond the artifact reference authorized by Pocket. Pocket remains responsible for its authenticated browser response and artifact rendering.

## Secret and data isolation

- Use separate least-privilege secret stores/identities for Pocket signing, worker verification, worker model access, CRM broker authentication, persistence, and telemetry. Never place all values in one `.env` file, image, CI log, or browser bundle.
- Rotate Pocket signing keys with overlapping verify-only key IDs; worker deployment accepts an explicit active/retiring public-key set. Revocation removes a key ID and denies pending work signed with it unless a human explicitly reissues the request.
- Use a worker-only model credential scoped to the reviewed provider/model allowlist. It must not authorize account administration, training-data controls, billing changes, or other application workloads.
- The CRM broker credential is worker-scoped to the six fixed read operations and accepts only the server-derived tenant/opaque-handle contract. It cannot write, enumerate tenants, proxy arbitrary paths, export data, or call providers.
- Send a minimal, redacted DTO to the model. Never send secrets, raw identifiers, direct contact methods, raw notes, service tokens, browser data, or unrestricted CRM output. Model responses are untrusted and must be schema/size/PII-checked before immutable artifact persistence.
- Structured logs, metrics labels, traces, dead-letter records, and alerts use correlation/run IDs and coarse reason codes only; they must not contain prompts, model output, contacts, opaque handles, authorization headers, or secrets.

## Queue, cancellation, and retries

Pocket creates the immutable run/audit record and cost reservation before the worker accepts work. The worker atomically transitions only tenant-scoped runs through:

```text
queued -> running -> completed
queued -> cancelled
running -> cancel_requested -> cancelled
queued|running -> unavailable|failed
```

Terminal transitions are append-only audit events; cancellation never deletes a run, attempt, artifact reference, or audit record. A cancel command is separately signed by Pocket, binds the same tenant, run ID, correlation ID, and short expiry, and is idempotent. It prevents a queued run from starting and signals an in-flight model request; if a provider cannot abort, the result is discarded, no artifact is persisted, and the terminal audit state records the cancellation race.

The worker checks cancellation before each broker read, before model invocation, before artifact persistence, and before terminal completion. There are no autonomous/background run starts, scheduled retries, or replay workers outside a Pocket-originated, signed enqueue/retry command.

Retries are bounded and explicit:

- Retry only transient private-network, broker, persistence, or allowlisted-provider failures, with at most two retries after the original attempt and exponential backoff capped at 30 seconds.
- Never retry denials, signature/scope/handle failures, cancellation, model-policy/validation failures, or missing accounting/audit state.
- Each attempt gets its own immutable attempt/audit event but keeps the same run and correlation ID. A retry reuses the original normalized request and reservation; it cannot broaden tool input, select a new model, or create a second artifact.
- If a retry could leave cost unknown or exceed the signed reservation, mark the run unavailable/failed and require a new Pocket request. No hidden spend or unbounded queue replay is permitted.

## Model routing, limits, and cost controls

The worker loads the immutable `copilot-foundation-v1` limits and its reviewed server-side routing table at deployment. It does not read route/model/provider selection from the body or browser. Initial execution is restricted to the foundation limits: one concurrent run per actor, four per organization, 20 starts per actor/hour, 10 read calls per actor+organization/minute, 8,000 input tokens, 1,500 output tokens, 12,000 artifact bytes, USD 0.25 estimated cost/run, and USD 10.00 estimated organization cost/day.

Before a run starts, atomic persistence-backed guards reserve actor/org concurrency, rate capacity, and the maximum model cost. The worker rechecks remaining output/cost budget before model invocation and artifact write. It releases unused reserved cost only at terminal accounting. Missing pricing, token accounting, a limit counter, reservation, policy version, or audit writer is an `unavailable` denial—not an unmetered fallback.

The routing table maps only the reviewed R1 `next_action_plan` class to the lowest-cost compliant approved model. R0 tools never invoke a model. Fallback requires another explicitly approved route with identical privacy, token, and existing-reservation constraints; otherwise it returns neutral unavailability. No default Hermes, public-chat model, user-selected provider/model, generic agent/tool registry, or external tool can be a fallback.

## Health, metrics, and alerting

Private-only readiness/liveness endpoints expose no customer or configuration data:

- `live`: process can serve private traffic.
- `ready`: policy loaded; signed-key set loaded; persistence/audit/counter dependencies reachable; no startup configuration error. It does not probe models with customer data.
- `healthz`: authenticated private operational summary with dependency statuses and policy/contract versions only.

Emit bounded, redacted metrics tagged by service, deployment, policy version, tool name, route class, outcome/reason code, and tenant-safe aggregate bucket—not actor, organization, request body, or prompt. Required counters/gauges include queue depth/age, accepted/denied/cancelled/completed/failed runs, retry count, signature and replay denials, active actor/org reservations, broker/model latency/errors, token/cost reserved versus settled, artifact validation failures, audit-write failures, and dependency readiness.

Alert on audit/counter/persistence dependency failure, cost reservation mismatch, replay/signature anomaly, sustained queue age, failed cancellation, unexpected egress denial, key-rotation verification failure, or cross-tenant scope mismatch. Alerts retain only correlation IDs and redacted reason codes. Operators investigate through the immutable Copilot audit view, not raw worker logs.

## Audit correlation and rollback

Pocket creates one correlation ID that appears in the Pocket request audit, run, every worker attempt, broker invocation, model usage reservation/settlement, artifact reference, cancellation, and terminal result. Audit records contain policy/contract version, signing key ID, signed-body fingerprint, tenant-safe actor/organization references, tool/risk class, route class, limits/reservation, timestamps, status/reason code, and redacted counts. They never contain keys, raw prompts, model payloads/responses, contact data, or raw CRM IDs.

Rollback is configuration-first: disable Pocket enqueue and route all new requests to a neutral unavailable response, drain/cancel queued jobs with signed cancel commands, preserve audit/usage records, and revoke the worker model/broker credentials if isolation is suspected. Do not repoint Copilot work to default Hermes, public chat, or a shared worker as an emergency fallback. Re-enable only after a reviewed deployment restores the same private network, signing, policy, audit, and budget gates.

## Activation prerequisites

The downstream private-worker provisioning card remains blocked pending human infrastructure approval. Before activation, verify a dedicated private host/project, no public ingress/DNS, Pocket-only mTLS identity, public-key verification and replay denial, separate least-privilege secrets, restrictive egress, private health access, immutable persistence/audit availability, atomic limit/cost reservations, cancellation race behavior, redacted telemetry, and rollback disablement. Then replay one authorized R0 request and one bounded R1 plan through Pocket with audit, artifact, and cost read-back. No R2/R3 action is part of activation.
